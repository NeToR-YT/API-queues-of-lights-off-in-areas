## Інтеграція з MongoDB

Проект було переведено з використання JSON-файлів на MongoDB для покращення продуктивності та надійності.

### Як запустити базу даних

1.  **Встановлення MongoDB**: Переконайтеся, що на вашому комп'ютері встановлено [MongoDB Community Server](https://www.mongodb.com/try/download/community) та [MongoDB Compass](https://www.mongodb.com/try/download/compass).
2.  **Запуск служби**: База даних зазвичай запускається автоматично як служба Windows. Ви можете перевірити це через "Служби" (Services.msc), знайшовши `MongoDB Server`.
3.  **Налаштування підключення**: У файлі `public/backend/config.json` вкажіть ваш URI підключення (за замовчуванням: `mongodb://localhost:27017/`) та назву бази даних.
4.  **Міграція даних**: Якщо ви переходите зі старої версії з JSON, запустіть скрипт міграції:
    ```bash
    python public/backend/migrate.py
    ```

### Структура бази даних (база `lightua`)

Дані розділені на кілька колекцій для зручного перегляду в Compass:

*   **`cities`**: Список областей та їх ID.
*   **`schedules_today`**: Актуальні графіки на сьогодні для всіх областей.
*   **`schedules_tomorrow`**: Графіки на завтра (якщо доступні).
*   **`schedules_history`**: Повний архів усіх графіків за всі дати.
*   **`today_sorted`** та **`tomorrow_sorted`**: Спеціальні представлення (Views), які завжди відсортовані за номером області (`channel_id`) для зручності в Compass.

### Переваги нової структури
*   **Швидкість**: API миттєво знаходить потрібні графіки за допомогою індексів.
*   **Наочність**: У Compass ви бачите "сьогодні" та "завтра" в окремих вкладках.
*   **Надійність**: Дані захищені від пошкодження при одночасному доступі.

РОЗДІЛ 1. ОРГАНІЗАЦІЙНА ХАРАКТЕРИСТИКА БАЗИ ПРАКТИКИ

1.1. Дослідження історії створення та структури установи
Backend LightUA-main створено для вирішення актуальної проблеми — автоматизації збору графіків відключення світла. Структура backend: папка backend містить ключові файли — app.py (Flask API), fetcher.py (парсер Telegram), config.json (налаштування), cities.json (дані міст), requirements.txt (залежності), session_name.session (файл сесії). Система побудована на Python, використовує Flask для API, Telethon для роботи з Telegram, APScheduler для автоматичного оновлення даних.

1.2. Опис та аналіз комп'ютерної техніки відділу, в якому проходила практика
Для роботи backend використовується сервер або комп’ютер з ОС Windows чи Linux, встановленим Python 3. Необхідний доступ до Інтернету, достатньо оперативної пам’яті для роботи парсера та API, дисковий простір для зберігання даних. Система не потребує складного обладнання, але важлива стабільність з’єднання та регулярний доступ до Telegram-каналів.

1.3. Аналіз програмного забезпечення відділу
Основне ПЗ: Python 3, Flask (створення API), APScheduler (планувальник задач), Telethon (Telegram-клієнт). Встановлення залежностей через requirements.txt. Для зберігання даних використовується формат JSON. Конфігураційні файли дозволяють гнучко налаштовувати параметри роботи, зокрема список каналів, таймінги оновлення, шляхи до файлів сесії.

1.4. Аналіз прикладних програм спеціального призначення, що використовувалися на базі практики
Парсер Telegram (fetcher.py) автоматично отримує повідомлення з каналів, аналізує їх, зберігає графіки у JSON-файли. API (app.py) надає доступ до даних через HTTP-запити. Конфігураційні файли дозволяють гнучко налаштовувати параметри роботи. Система підтримує ручний запуск оновлення, автоматичне оновлення кожні 15 хвилин, обробку помилок та логування.

2.1. Опис та аналіз поставлених завдань від керівника практики
Завдання: автоматизувати збір графіків відключення, забезпечити регулярне оновлення, надати API для frontend, забезпечити стабільність та надійність роботи, обробку аварійних графіків, підтримку історії змін.

2.2. Вибір мови програмування для створення програмного продукту
Обрано Python через зручність роботи з Telegram, наявність бібліотек для парсингу та API, простоту розгортання, підтримку багатьох платформ. Flask обрано для створення REST API, Telethon — для інтеграції з Telegram, APScheduler — для автоматизації оновлення.

2.3. Тестування створеного програмного продукту
Тестування проводилось на декількох рівнях: перевірка роботи парсера, коректності збереження даних, стабільності API, перевірка автоматичного оновлення даних, обробки помилок. Виявлені проблеми (наприклад, розбіжність часових поясів) оперативно виправлялися командою. Система тестувалася як розробниками, так і фокус-групою користувачів.

2.4. Впровадження створеного програмного продукту та його оцінка
Backend інтегровано з frontend, забезпечено регулярне оновлення даних, API працює стабільно, дані доступні для користувачів у зручному форматі. Система готова до масштабування, підтримує історію змін, аварійні графіки, статистику по відключеннях. Проект має перспективи розвитку: додавання пошуку за адресою, сповіщення про зміни, інтерактивна карта, розширена аналітика.
