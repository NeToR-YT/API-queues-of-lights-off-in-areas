# ADR-0003. Модель даних v2

- **Статус:** запропоновано 2026-10-30, на розгляді.
- **Контекст:** парсер пише в MongoDB, API читає. Це їхній єдиний зв'язок, тож схема
  даних і є контрактом між ними. Сумісність схеми зі старим бекендом не потрібна:
  перехідний `/api/*` лише перетворює нові документи на старий формат.

## Рішення

Схеми лежать у `docs/contracts/`, кожен документ має поле `schema_version`.

| Колекція | Документ | Унікальний ключ |
|---|---|---|
| `schedules` | графік каналу на дату | `channel_id` і `schedule_date` |
| `parse_state` | останнє прочитане повідомлення каналу | `channel_id` |
| `heartbeat` | стан останнього циклу | один документ |

Мітки часу зберігаються як рядки UTC у форматі `YYYY-MM-DDTHH:MM:SSZ`: їх однаково
читає будь-яка мова, і вони правильно сортуються як текст. Інтервал відключення
записується місцевим часом із поста у форматі `HH:MM-HH:MM`. Якщо кінець раніше за
початок, інтервал переходить через північ.

### Що свідомо не переносимо зі старого бекенда

1. **Колекції `schedules_today`, `schedules_tomorrow`, `schedules_history`.** «Сьогодні» й
   «завтра» стають звичайним запитом за датою, окреме сховище для них не потрібне. Разом
   із ним зникає нічне перекладання даних між колекціями та його помилки.
2. **Підстановку графіка з іншої дати як сьогоднішнього.** Користувач бачив би чужий день
   під сьогоднішньою датою. Якщо графіка немає, API відповідає 404.

## Відкрите питання: як застосовувати оновлення графіка

Старий парсер додає інтервали нового поста до вже збережених. Якщо обленерго скасує
відключення оновленим графіком, скасований інтервал лишиться в базі назавжди.

Замінити чергу повністю новим постом теж не можна. Оновлення часто містять лише змінені
або додані діапазони, а не весь день (наприклад, коли пів дня вже минуло), і заміна
стерла б решту графіка.

Рішення відкладено до реальних прикладів постів-оновлень із Telegram-каналів: правило
треба вивести з них. Від нього залежить логіка запису, але не схема. Можливо, у
`schedules` доведеться зберігати всі пости за день, щоб перераховувати графік.

## Наслідки

**Переваги.** Один запит за датою замість трьох колекцій. Поле `source` дозволяє
простежити кожен запис до поста. Для історії не потрібна окрема логіка.

**Недоліки.** Логіка розбору зі старого парсера не перевіряє межі часу: «08-99» дасть
`08:00-99:00`. Тому перед записом документ треба перевіряти за схемою, а відкинуте логувати.
