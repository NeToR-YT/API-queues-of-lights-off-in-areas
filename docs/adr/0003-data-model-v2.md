# ADR-0003. Модель даних v2

- **Статус:** запропоновано (2026-10-30), чекає на рев'ю Oleksiy.
- **Контекст:** парсер пише в Mongo, API читає. Це їхній єдиний зв'язок, тож схема і є
  контрактом. Сумісність схеми зі старим бекендом не потрібна: перехідний `/api/*` буде
  тонким мапером над новою схемою.

## Рішення

Схеми — у `docs/contracts/`, кожен документ має `schema_version`.

| Колекція | Документ | Унікальний ключ |
|---|---|---|
| `schedules` | графік каналу на дату | `channel_id` + `schedule_date` |
| `parse_state` | останнє прочитане повідомлення каналу | `channel_id` |
| `heartbeat` | стан останнього циклу | один документ |

Час — рядки UTC у форматі `YYYY-MM-DDTHH:MM:SSZ`: однаково читаються будь-якою мовою і
сортуються як текст. Початок і кінець інтервалу — місцевий час із поста, `HH:MM-HH:MM`;
кінець раніше за початок означає перехід через північ.

### Що свідомо не переносимо зі старого бекенда

1. **Колекції `schedules_today`, `schedules_tomorrow`, `schedules_history`.** «Сьогодні» і
   «завтра» — це запит за датою, а не окреме сховище. Зникає нічна ротація даних між
   колекціями разом із її помилками.
2. **«Fallback» — графік на іншу дату, записаний як сьогоднішній.** Користувач бачив би
   чужий день під сьогоднішньою датою. Нема графіка — API чесно відповідає 404.

## Відкрите питання: що робити з оновленням графіка

Старий парсер **об'єднує** інтервали нового поста зі збереженими. Якщо обленерго скасує
відключення оновленим графіком, скасований інтервал лишиться в базі назавжди.

Просте «новий пост заміняє чергу» теж не підходить: за спостереннями Oleksiy, оновлення часто
містить **лише змінені або додані діапазони**, а не весь день (наприклад, коли пів дня вже
минуло). Заміна стерла б решту графіка, об'єднання не прибирає скасоване.

**Рішення відкладено** до реальних прикладів постів-оновлень із Telegram-каналів: правило
виводимо з них, а не вгадуємо. Це блокує логіку запису в задачі 1.5, але не схему: можливо,
доведеться додати до `schedules` історію постів дня, щоб перераховувати графік.

## Наслідки

**Добре.** Один запит за датою замість трьох колекцій; `source` дає простежити кожен запис
до поста; історія не потребує окремої логіки.

**Погано.** Домен старого парсера не перевіряє межі часу: «08-99» дасть `08:00-99:00`.
Адаптер Mongo (1.5) мусить валідувати документ за схемою і логувати відкинуте.
