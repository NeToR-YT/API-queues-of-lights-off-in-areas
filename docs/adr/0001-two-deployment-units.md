# ADR-0001. Два окремі сервіси: парсер і платформа

- **Статус:** ухвалено 2026-07-06. Вибір Java для платформи замінено на Python
  ([ADR-0002](0002-python-backend.md)). Поділ на два сервіси, ізоляція сесії та обмін
  даними через MongoDB лишаються чинними.
- **Контекст:** один розробник і слабкий сервер. Telegram-сесію треба тримати ізольовано.
  На момент рішення Java була потрібна для портфоліо й дипломної роботи.

## Рішення

Рівно два сервіси, без мікросервісної архітектури:

1. `parser`: Python і Telethon, фоновий процес без вхідних портів. Пише розклади в
   MongoDB під користувачем з мінімальними правами.
2. `platform`: модульний моноліт (на момент рішення Java Spring Boot). Читає ту саму
   базу під власним користувачем лише для читання й віддає публічний `/v1`.

Сервіси обмінюються даними через спільну MongoDB. База працює як replica set з одного
вузла (`--replSet rs0`), що дає Change Streams: платформа дізнається про зміну розкладу
без окремого брокера повідомлень.

## Наслідки

**Переваги.** Telegram-сесія замкнена в одному контейнері з мінімальними правами. Падіння
платформи не зупиняє збір даних. Сервер тягне два процеси, а не сім. Telegram зберігає
повідомлення сам, тож коли MongoDB недоступна, парсер просто пропускає цикл, а
`parse_state.last_message_id` дозволяє пізніше дочитати пропущене без втрат.

**Недоліки.** Спільна база пов'язує сервіси через схему даних. Щоб це не заважало, схема
описана явно: JSON Schema документа розкладу, поле `schema_version`, golden-тести з обох
боків і терпимий до змін читач на боці платформи.

**Відкладено.** Брокер повідомлень (NATS чи RabbitMQ) знадобиться лише тоді, коли
з'являться зовнішні споживачі подій. Доти він лише ускладнює експлуатацію.

## Альтернативи

- *Усе на Java, включно з парсером.* Відкинуто: бібліотеки для Telegram у Python зріліші,
  а тримати сесію в окремому процесі вимагає безпека.
- *Окремий мікросервіс на кожну область чи функцію.* Відкинуто: для одного розробника й
  одного слабкого сервера витрати на підтримку більші за будь-яку вигоду.
