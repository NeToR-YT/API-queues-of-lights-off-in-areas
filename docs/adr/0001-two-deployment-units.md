# ADR-0001. Два деплой-юніти: Python-парсер і Java-платформа

- **Статус:** ухвалено (2026-07-06); **технологічна частина (Java) заміщена [ADR-0002](0002-python-backend.md)**. Принцип двох юнітів, ізоляція сесії й інтеграція через Mongo — у силі.
- **Контекст:** один розробник, слабкий домашній ARM-сервер, вимога тримати
  Telegram-сесію ізольованою, Java потрібна в портфоліо як дипломна складова.

## Рішення

Рівно **два** деплой-юніти, не мікросервіси:

1. `parser` — Python/Telethon, headless worker, **без вхідних портів**.
   Пише розклади в MongoDB під least-privilege юзером.
2. `platform` — Java Spring Boot, модульний моноліт (Spring Modulith).
   Читає ту саму Mongo під власним read-only юзером, віддає публічний `/v1`.

Інтеграція — через спільну MongoDB. Mongo піднімається як single-node replica
set (`--replSet rs0`), що дає **Change Streams**: платформа отримує події
«розклад змінився» без брокера повідомлень.

## Наслідки

**Добре.** Telegram-сесія замкнена в одному контейнері з мінімальними правами;
падіння платформи не зупиняє збір даних; ARM-сервер тягне два процеси, а не сім.
Telegram сам є durable-буфером — при недоступній Mongo парсер пропускає цикл,
а `parse_state.last_message_id` дозволяє дочитати пропущене пізніше без втрат.

**Погано.** Спільна БД — це зчеплення через схему даних. Пом'якшуємо явним
контрактом: JSON Schema документа розкладу + поле `schema_version`, golden-тести
з обох боків, tolerant reader на боці Java.

**Відкладено.** Брокер (NATS/RabbitMQ) — лише якщо з'являться зовнішні консюмери.
Поки їх нема, він додає операційну вартість без вигоди.

## Альтернативи

- *Все на Java, парсер теж.* Відкинуто: екосистема Telegram-клієнтів у Python
  зріліша, а ізоляція сесії в окремому процесі — вимога безпеки.
- *Мікросервіси на кожну область/фічу.* Відкинуто: один розробник, один слабкий
  сервер; вартість експлуатації переважує будь-яку вигоду.
