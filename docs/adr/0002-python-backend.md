# ADR-0002. Увесь бекенд на Python

- **Статус:** ухвалено 2026-10-26. Замінює вибір Java з ADR-0001.
- **Контекст:** проєкт перестав бути дипломною роботою, тож аргумент «Java для портфоліо
  й захисту» зник. Головний критерій тепер ощадливість: невеликий сервер має тримати
  бекенд і кілька Telegram-ботів.

## Рішення

- Парсер і API пишемо на Python, API на FastAPI.
- Два процеси з ADR-0001 лишаються: ізольований парсер із Telegram-сесією й без портів та
  API, який лише читає базу. Злам чи вразливість публічного API не дає доступу до сесії.
- Контракт: новий `/v1` і перехідний `/api/*` у тому ж форматі, що й у TS-бекенді.
- Основа коду: функції розбору беремо з Python-прототипу (тег `archive/python-flask-prototype`,
  файл `backend/fetcher.py`, з якого колись перенесли TS-парсер) і додаємо доробки з TS.
  Інфраструктуру прототипу (JSON-файли, Flask, subprocess) не беремо. Еталоном поведінки
  слугує golden-корпус.

## Наслідки

**Переваги.** Після відмови від TS на сервері лишиться одне середовище виконання.
Найзріліша бібліотека для Telegram (Telethon), aiogram для ботів, зручна база для
майбутнього розпізнавання картинок і прогнозування.

**Недоліки.** Python і Node споживають приблизно однаково пам'яті (40-100 МБ на процес),
тож сам перехід ресурсів не економить. Економія йде від обмеження кешу MongoDB, малої
кількості процесів і одного середовища виконання.

## Альтернативи

- *Лишитися на TypeScript.* Технічно рівноцінний варіант, і нічого не довелося б
  переписувати. Відкинуто на користь екосистеми Python.
- *Java і Spring Boot.* Найгірший варіант для слабкого ARM-сервера: 200-400 МБ на JVM і
  повільний старт.
- *Go.* Найощадливіший (10-30 МБ на процес). Відкладено, поки ресурси не стануть вузьким місцем.
