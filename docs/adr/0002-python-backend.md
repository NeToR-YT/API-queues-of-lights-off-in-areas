# ADR-0002. Увесь бекенд на Python; Java скасовано

- **Статус:** ухвалено (2026-10-26). Заміщує технологічну частину ADR-0001.
- **Контекст:** проєкт перестав бути дипломним і став пет-проєктом. Аргумент
  «Java для портфоліо й захисту» зник. Головний критерій тепер — ощадливість:
  слабкий домашній ARM-сервер має тримати бекенд і кілька Telegram-ботів.

## Рішення

- **Парсер і API — Python.** API на **FastAPI**.
- **Два процеси лишаються** (з ADR-0001): ізольований парсер із TG-сесією без портів
  і API, що тільки читає Mongo. Злам чи вразливість публічного API не дає доступу до сесії.
- **Контракт:** новий `/v1` + перехідний `/api/*` тієї ж форми, що в TS-бекенді.
- **Основа коду:** доменні функції парсингу беремо з Python-прототипу (`back:backend/fetcher.py`,
  з якого колись портовано TS-парсер) і докочуємо доробки з TS. Інфраструктуру прототипу
  (JSON-файли, Flask, subprocess) не беремо. Еталон поведінки — golden-корпус.

## Наслідки

**Добре.** Один рантайм на сервері після виводу TS. Найзріліша Telegram-бібліотека
(Telethon), aiogram для ботів, природна синергія з майбутніми OCR і ML.

**Погано.** Python і Node по RAM на одному рівні (~40–100 МБ на процес), тож перехід
сам по собі ресурсів не економить. Економія — від ліміту кешу Mongo, малої кількості
процесів і одного рантайму, а не від мови.

## Альтернативи

- *Лишитися на TypeScript.* Технічно рівноцінно й без переписування — це була порада
  на момент рішення. Відкинуто власником проєкту на користь екосистеми Python.
- *Java / Spring Boot.* Найгірше для слабкого ARM: 200–400 МБ на JVM, повільний старт.
- *Go.* Найощадливіше (10–30 МБ на процес); відкладено, поки ресурси не стануть вузьким місцем.
